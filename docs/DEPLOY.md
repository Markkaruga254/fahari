# Production deployment (Render)

Frontend and backend are **separate Render services**, both auto-deploying
from `main`.

## Frontend

```text
Service: fahari-dashboard
URL:     https://fahari-dashboard.onrender.com
Runtime: Node
Root Directory: repository root
Build:   cd frontend && npm install && npm run build
Start:   cd frontend && npm start
Branch:  main (auto deploy enabled)
```

`/` is a static landing page. `/dashboard` renders on demand and calls the
backend at request time, so the build needs no running backend. Without
`BACKEND_URL`/`DASHBOARD_API_KEY`, `/dashboard` shows a friendly
"not configured" message instead of crashing.

## Backend

```text
Service: peoples-priorities-api-gsvz
URL:     https://peoples-priorities-api-gsvz.onrender.com
Runtime: Docker (see render.yaml, health check /ready)
```

The backend service is defined in `render.yaml`. The frontend service is
configured in the Render dashboard (it is not in `render.yaml`).

## Environment variables (names only, never values)

Frontend service:

| Variable | Notes |
|---|---|
| `NEXT_PUBLIC_USSD_CODE` | Placeholder `*384*XXXX#`. Baked in at build time: changing it needs a redeploy. |
| `NEXT_PUBLIC_VOICE_NUMBER` | Placeholder `Voice line (demo)`. Same rebuild note. |
| `BACKEND_URL` | Backend base URL. Server-side only. |
| `DASHBOARD_API_KEY` | Same value as the backend. Server-side only — **never** a `NEXT_PUBLIC_` variable. |

Backend service variables are defined in `render.yaml` (`DATABASE_URL`,
`WEBHOOK_SECRET`, `PHONE_HASH_PEPPER`, `DASHBOARD_API_KEY`, AT_* settings).

## Troubleshooting

**Use `npm install`, not `npm ci`, for the frontend build.** The repo has no
committed `frontend/package-lock.json`, so `npm ci` fails on Render. The
verified build command is `cd frontend && npm install && npm run build`.
Do not create a fake lockfile. Committing a real lockfile (generated by a
clean `npm install`) would be a worthwhile future hardening step — at that
point the build can switch back to `npm ci`.

## Update workflow

- Small commits to `main` go straight to production (auto deploy).
- Risky changes go on a branch first and get a preview URL before merging.
